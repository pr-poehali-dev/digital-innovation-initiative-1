## 3. Таблица 8. Участники коллегиальных органов

**Включена по вашему решению.** Текстового поля недостаточно.

### 3.1. Состав полей

| Поле | Обязательность | Описание |
|---|---|---|
| Коллегиальный орган | Обязательно | Ссылка на `collegial_body` |
| Лицо | Условно | Ссылка на `person` |

**Ограничение:** должно быть заполнено **либо** лицо, **либо**
организационная позиция — проверка на уровне БД.

### 3.2. Назначение позиции вместо лица

Поддерживаются оба способа:

| Способ | Когда применяется | Преимущество |
|---|---|---|
| Конкретное лицо | Персональное включение в состав | Точность |
| **Организационная позиция** | Постоянный состав по должности | **Не требует переписывания при кадровой замене** |

### 3.3. Что это даёт

| Возможность | Реализуется |
|---|---|
| Состав на конкретную дату | Да — через даты начала и окончания |
| Проверка полномочий участника | Да — через основание включения |
| Замена и временное исполнение | Да — новая запись с датами |
| Проверка кворума **по составу** | Да — подсчёт членов с правом голоса |
| Выявление дублей | Да — ограничение уникальности |
| История состава | Да — записи не удаляются |
| Различение членов и приглашённых | Да — роль в органе + право голоса |

### 3.4. Явное ограничение MVP

**Индивидуальное голосование каждого участника в MVP
не хранится.** Факт соблюдения кворума подтверждается протоколом.

**Автоматическая проверка фактического кворума на заседании
в MVP не реализуется и не обещается.** Для неё потребуется
отдельная модель присутствия и голосования — второй этап.

Что проверяется в MVP: соответствие **списочного** состава
с правом голоса установленному кворуму. Это проверка
правоспособности органа, а не факта заседания.

## 4. Таблица 15. `source_ref` — единая сущность

**Остаётся единой** по вашему решению. Разделения на две таблицы
не производится.

### 4.1. Разделение документа и способа использования

Ключевое требование выполнено: семантика определяется **типом
использования**, а не дублированием документа.

```
source_ref (запись об использовании документа)
  ├─ Свойства ДОКУМЕНТА:
  │    тип · наименование · номер · дата · пункт или раздел
  │    срок действия · ссылка или вложение · статус проверки
  │    признак конфиденциальности · дата фиксации · автор фиксации
  │
  └─ Свойства ИСПОЛЬЗОВАНИЯ:
       тип сущности · идентификатор сущности · имя поля
       ТИП ИСПОЛЬЗОВАНИЯ:
         · является основанием полномочия
         · подтверждает решение
         · содержит требование
         · служит информационным источником
```

### 4.2. Один документ — несколько записей

**Ограничение зафиксировано явно.**

В предлагаемой модели одна запись `source_ref` = одно
использование документа в одной записи. Один документ,
обосновывающий пять полномочий, порождает **пять записей**
с повторяющимися реквизитами.

| Вариант | Таблиц | Оценка |
|---|---|---|
| **Текущий:** повтор реквизитов в каждой записи | 16 | Простота, дублирование текста |
| Альтернативный: отдельная таблица документов + таблица использований | **17** | Нормализация, +1 таблица |

**Фиксирую как осознанное ограничение MVP:** реквизиты документа
дублируются при многократном использовании. Изменение реквизитов
потребует обновления всех записей.

**Не создаю дополнительную таблицу без вашего решения.** Если
нормализация необходима — реестр становится **17 таблиц**.

## 6. Матрица четырёх системных ролей: 13 операций

### 6.1. Условия утверждения — выполнение

| Ваше условие | Реализация |

**\*\*** Только конфиденциальные поля своих инициатив;
конфиденциальные источники — по отдельному разрешению.

### 6.3. Правило независимой проверки

| Ситуация | Результат |
|---|---|
| Редактор подтверждает сведения другого участника | **Разрешено** |
| Редактор подтверждает **свои** сведения | **Запрещено**, блокирующая ошибка |
| Управляющий кабинетом подтверждает свои сведения | Разрешено — он вышестоящий проверяющий |

### 6.4. Различия ролей — проверка

Проверено по всем 13 операциям: **ни одна пара ролей не имеет
одинакового набора прав**.

| Пара | Первое различие |
|---|---|
| `sys_admin` / `sys_manager` | Операции 4, 5, 10, 13 |
| `sys_admin` / `sys_editor` | Операция 1 (область), 11 |
| `sys_admin` / `sys_viewer` | Операция 2 |
| `sys_manager` / `sys_editor` | Операции 5, 11, 13 |
| `sys_manager` / `sys_viewer` | Операция 2 |
| `sys_editor` / `sys_viewer` | Операция 2 |

**Разные области доступа внутри одной роли** решаются
**областью назначения**, а не созданием новых ролей. Например,
руководитель Группы и владелец инициативы — оба `sys_editor`,
различаются перечнем назначенных инициатив.

**Новые роли в продукте не создаю.**
