# Пакет на согласование. Часть 6. Тестовая обезличенная инициатива

**ВСЕ ДАННЫЕ ЭТОГО РАЗДЕЛА — ТЕСТОВЫЕ.**
Условные обозначения лиц. Оценки влияния, заинтересованности и
отношения являются проверочными и **не относятся к реальным
должностным лицам**. Полномочия реальным лицам не назначаются.
Цель — выявить методологические ошибки модели до создания таблиц.

**ЛИЦО-01 · Руководитель Блока внутреннего контроля**

Опасения: дополнительная нагрузка на подразделения.
Полномочия: утверждает приоритеты, распоряжается ресурсами Блока.
Может заблокировать: включение в бюджет.
Стратегия: активно вовлекать. Ответственный: ЛИЦО-02.

**ЛИЦО-02 · Руководитель Группы**

**ЛИЦО-03 · Владелец инициативы**

Полномочия: принимает большинство решений по инициативе.
Стратегия: активно вовлекать.

**ЛИЦО-04 · Руководитель инициативы**
Ожидания: понятные требования, реалистичные сроки.
Опасения: изменение объёма в ходе реализации.
Полномочия: готовит материалы, ведёт оперативную работу.

**ЛИЦО-05 · Представитель функционального заказчика**
Ожидания: сокращение ручного сбора данных.

Полномочия: согласовывает требования, подтверждает потребность.

Полномочия: согласовывает техническую реализуемость.
Может заблокировать: запуск пилота.
**Стратегия взаимодействия отсутствует — предупреждение W03.**

**ЛИЦО-07 · Представитель информационной безопасности**
Ожидания: соблюдение требований к защите сведений.
Опасения: обработка сведений вне контролируемого контура;
отсутствие требований к защите на старте.
Полномочия: согласовывает требования к данным и безопасности.
Может заблокировать: запуск пилота.
Риск сопротивления: высокий.
Стратегия: снижать сопротивление. Ответственный: ЛИЦО-03.
**Ближайшее действие просрочено: встреча 08.08 — W04.**

## 5. Сценарии методологической проверки

### Сценарий 1. Нормальная модель

**Объект:** решение №9 «Разрешить запуск пилота».
**Условие:** все роли назначены, ровно один принимающий, маршрут
определён, эскалация указана.
**Ожидаемое поведение:** ошибок нет; система показывает маршрут
из 9 шагов; возможен перевод в статус «подтверждено».
**Что проверяет:** базовую работоспособность модели.
**Результат на тестовых данных:** ✓ модель отрабатывает.
Отдельно фиксируется предупреждение о незаполненных материалах —
это корректное поведение, не ошибка модели.

---

### Сценарий 2. Нет принимающего решение

**Объект:** решение №6 «Определить требования к данным и безопасности».
**Условие:** есть готовящий, рекомендующий и два согласующих,
но нет ни одного участника с видом «принимает окончательное решение».
**Ожидаемое поведение:** блокирующая ошибка **E01**; невозможен
переход в статус «подтверждено»; в матрице ячейка помечена **?**;
на главном экране — в блоке блокирующих ошибок; предложено действие
«Назначить принимающего».
**Что проверяет:** система не допускает решения без ответственного
за окончательный выбор.
**Результат:** ✓ ошибка выявляется детерминированным правилом.

**Выявленный методологический риск:** согласование ИБ формально есть,
но решение не может быть принято. Это тупик, который в реальной
работе приводит к скрытой остановке инициативы. Подтверждает
необходимость проверки E01.

---

### Сценарий 3. Два принимающих решение

**Объект:** решение №7 «Определить приоритет».
**Условие:** куратор и владелец инициативы оба имеют вид участия
«принимает окончательное решение»; модель коллегиального решения
не указана.
**Ожидаемое поведение:** блокирующая ошибка **E02**; предложены
варианты разрешения: (а) оставить одного принимающего,
(б) указать порядок коллегиального решения — единогласно,
большинством, при равенстве голос председательствующего,
(в) разделить на два разных решения.
**Что проверяет:** отсутствие двоевластия в принятии решений.
**Результат:** ✓ конфликт выявляется.

**Выявленный методологический вопрос:** нужна ли отдельная сущность
«Коллегиальный порядок принятия решения» либо достаточно поля
в экземпляре решения? **Выношу на согласование.**

---

### Сценарий 4. Влиятельный стейкхолдер без стратегии

**Объект:** ЛИЦО-06 — представитель информационных технологий,
влияние 4, заинтересованность 2, отношение «сомневается».
**Условие:** стратегия взаимодействия не заполнена.
**Ожидаемое поведение:** предупреждение **W03**; на матрице
«влияние × заинтересованность» точка попадает в сектор
«Поддерживать удовлетворённость»; ИИ формирует **AI-черновик**
стратегии с обоснованием; черновик **не применяется автоматически**,
требует подтверждения.
**Что проверяет:** предупреждения не блокируют работу; AI-предложения
не подменяют решение человека.
**Результат:** ✓ предупреждение формируется, AI-черновик изолирован.

**Дополнительно выявлено:** ЛИЦО-07 (влияние 5, возражает) имеет
просроченное действие — предупреждение **W04**. Сочетание высокого
влияния, возражения и просрочки — наиболее критичная комбинация;
предлагаю выделять её отдельно на главном экране.

### Сценарий 5. Ответственность без полномочий

**Объект:** роль «Владелец эффекта» (ЛИЦО-02).
**Условие:** роль отвечает за достижение эффекта и его подтверждение,
но по решению №12 имеет вид участия «рекомендует», а не «принимает».
Ни в одном из 12 решений роль не принимает окончательное решение.
**Ожидаемое поведение:** предупреждение **W09** «Ответственность
без полномочий»; система показывает, за какой результат роль отвечает
и каких прав ей не хватает; предложены варианты: наделить правом
принятия по решению №12, либо снять ответственность, либо явно
указать маршрут эскалации.
**Что проверяет:** выявление дефекта модели управления, невидимого
в обычной матрице RACI.
**Результат:** ✓ дефект выявляется.

**Проверка обратной ситуации (W10):** роль «Куратор инициативы»
принимает решения №3, №7, №11, но не отвечает ни за один эффект.
Это «полномочия без ответственности» — предупреждение W10.
На тестовых данных также выявляется.

**Обнаруженные методологические пробелы:**

1. **Основание полномочия.** В тестовой модели у большинства участий
   в решениях основание не указано, поскольку порядок проектного
   управления организации мне неизвестен. Правило E05 сработает
   массово. Нужно решение: делать ли основание обязательным сразу
   или вводить переходный период.

2. **Коллегиальные решения.** Требуется отдельная сущность или поле —
   вопрос открыт.

3. **Зависимости между решениями.** Решение №9 невозможно без №6.
   В модели данных зависимость между экземплярами решений
   **не предусмотрена**. Предлагаю добавить связь
   «решение → предшествующее решение». **Пробел модели, выявленный
   тестированием.**

4. **Роль «Группа»** — коллегиальный орган, а не лицо. В матрице
   она присутствует как столбец. Требуется подтверждение, что
   коллегиальный орган моделируется как роль, а не отдельная сущность.

5. **Условное обозначение лиц.** Формат «ЛИЦО-NN» рабочий, но при
   переходе к реальным данным потребуется миграция обозначений.
   Предлагаю сразу хранить внутренний код лица отдельно
   от отображаемого имени.
