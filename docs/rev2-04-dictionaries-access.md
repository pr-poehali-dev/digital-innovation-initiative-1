## 1. Справочники: разделение на три группы

Единая универсальная таблица для всех 19 справочников
**не утверждается**. Ваши замечания приняты: слабые ограничения
целостности, риск ошибочных ссылок между типами, усложнение
валидации, невозможность специфических атрибутов.

### 1.1. Группа 1. Простые настраиваемые классификаторы — 12 видов

Хранятся в одной таблице `ref_classifier` с полем
`classifier_type`.

| Вид | Пример значений |
|---|---|
| Статус инициативы | идея, предложена, в реализации, завершена |
| Этап инициативы | инициация, концепция, пилот, внедрение |
| Форма реализации | проект, мероприятие, пилот, орг. изменение |
| Тип роли | кураторская, владельческая, управленческая |
| Уровень влияния | 1–5 |
| Уровень вовлечённости | 1–5 |
| Стратегия взаимодействия | активно вовлекать, информировать |
| Уровень эскалации | команда, владелец, Группа, руководитель |
| Статус решения | ожидает, на согласовании, принято |
| Статус исполнения | не начато, исполняется, исполнено |
| Тип источника | закон, положение, протокол, поручение |
| Уровень конфиденциальности | открыто, внутреннее, ограниченно |

**Обоснование однотипности:** все 12 имеют **идентичный** набор
атрибутов — код, наименование, описание, порядок, активность.
Ни один не требует дополнительных полей. Ни на один не опирается
логика проверок.

**Критерий отнесения:** значение можно переименовать, добавить
или деактивировать **без изменения кода приложения**.

---

### 1.2. Группа 2. Системные справочники — 6 видов

Хранятся в `ref_system_code`. Отдельная таблица, поскольку
требуют иных ограничений.

| Вид | Почему системный |
|---|---|
| Статус жизненного цикла | Коды `confirmed`, `approved` захардкожены в правиле E05 |
| Тип и происхождение | Код `typical_practice` запрещает отображение как AS IS |
| Уровень уверенности | Влияет на отображение и фильтрацию |
| Вид участия в решении | Код `decides` — основа правил E01, E02 |
| Тип зависимости решений | Код `mandatory_predecessor` управляет блокировкой |
| Состояние лица | Коды `dismissed`, `transferred` запускают предупреждение W19 |

**Ограничения группы 2:**
- `is_system = true` — **запрет удаления**;
- **запрет изменения кода** (наименование менять можно);
- добавление новых значений — только с изменением кода приложения;
- при попытке удаления — блокирующая ошибка.

---

### 1.3. Группа 3. Самостоятельные предметные сущности

**Не являются справочниками.** Не могут храниться как значения
универсальной таблицы:

| Сущность | Почему не справочник |
|---|---|
| `role_template` — роли | Имеет 10+ специфических атрибутов: полномочия, обязанности, признак единоличности, применимые этапы |
| `decision_type` — типы решений | Имеет этап, материалы, критерии, сроки, документ фиксации |
| `collegial_body` — коллегиальные органы | Имеет состав, кворум, порядок голосования |
| `org_unit` — подразделения | Существующая сущность с иерархией и связями |

**Критерий:** если объект имеет собственные атрибуты помимо
кода и наименования либо участвует в связях — это сущность,
а не значение справочника.

---

### 1.4. Ответы на ваши вопросы по универсальной модели

| Вопрос | Ответ |
|---|---|
| **Защита от ссылки на значение неверного типа** | Составной внешний ключ `(classifier_type, code)` с фиксированным значением типа в ссылающейся таблице. Проверка на уровне БД, не приложения |
| **Системный код** | Поле `is_system` в `ref_system_code`; триггер или проверка запрещает удаление и изменение кода |
| **Уникальность внутри вида** | `UNIQUE (classifier_type, code)` — уникальность в рамках вида, не глобально |
| **Порядок сортировки** | Поле `sort_order`, отдельная нумерация внутри каждого вида |
| **Активность и архивирование** | Поля `is_active`, `archived_at`. Физическое удаление запрещено |
| **Запрет удаления системных значений** | Ограничение на уровне БД: `CHECK` при попытке пометить системное значение архивным |
| **История изменений** | Через `mgmt_audit_log` — общий механизм |
| **Специфические атрибуты** | Если требуются — объект переводится в группу 3 как отдельная сущность |
| **Ссылочная целостность** | Составной внешний ключ; для группы 2 дополнительно запрет удаления |

**Итоговое обоснование разделения:** 12 классификаторов действительно
однотипны и не требуют прикладной валидации — для них составного
внешнего ключа достаточно. 6 системных требуют дополнительных
ограничений, поэтому вынесены отдельно. 4 предметные сущности
не маскируются под справочники.

Результат: **2 таблицы справочников** вместо 19 отдельных
и вместо 1 универсальной.

## 2. Правила валидации MVP

**18 детерминированных правил.** AI-рекомендации в MVP
не включаются.

### 2.1. Блокирующие ошибки — 9

| Код | Правило |
|---|---|
| `E01` | У решения нет участника с видом «принимает окончательное решение» |
| `E02` | Несколько независимых принимающих **без указания коллегиального порядка** |
| `E03` | У инициативы нет владельца |
| `E04` | Роль назначена, но не указано лицо, подразделение или коллегиальный орган |
| `E05` | Статус `confirmed`/`approved` без основания полномочия |
| `E08` | Статус `confirmed`/`approved` без указания источника |
| `E11` | У стейкхолдера не задано влияние или вовлечённость |
| `E13` | Коллегиальный орган без указанного кворума |
| `E14` | Коллегиальный орган без порядка голосования |

### 2.2. Предупреждения — 9

| Код | Правило |
|---|---|
| `W03` | Стейкхолдер с влиянием 4–5 без стратегии взаимодействия |
| `W05` | Превышено рекомендуемое число согласований (порог настраиваемый) |
| `W07` | Участник перегружен решениями (порог настраиваемый) |
| `W09` | **Ответственность без полномочий**: роль отвечает за результат, но не принимает ни одного связанного решения |
| `W10` | **Полномочия без ответственности**: роль принимает решения, но не отвечает ни за один результат |
| `W17` | Полномочие без основания в статусе черновика |
| `W18` | Полномочие без основания в статусе «на проверке» |
| `W19` | Лицо уволено или переведено, назначения ролей активны |
| `W21` | Зависимое решение принимается при невыполненном предшествующем условии |

Правило `W20` (заполнено «отношение» для реального лица) исключено —
поле не реализуется вовсе.

### 2.3. Правила зависимостей решений

| Правило | Тип |
|---|---|
| Нельзя перевести в «принято» при невыполненном обязательном предшествующем | Блокирующее |
| Административное исключение требует основания и уполномоченного лица | Блокирующее |
| Циклические зависимости запрещены | Блокирующее, проверка при создании |
| Изменение предшествующего решения формирует предупреждение по зависимым | Предупреждение |

### 3.3. Разделение технической и содержательной ролей

**Администратор НЕ может:** подтверждать данные · утверждать ·
просматривать чувствительные поля · разрешать административное
исключение зависимости.

Обоснование: администратор осуществляет техническое
администрирование. Содержательные управленческие решения —
компетенция руководителя кабинета.

### 3.4. Чувствительные поля MVP

После исключения оценочных характеристик остались:

- позиция по конкретному вопросу;
- условия поддержки;
- нерешённые вопросы;
- контактные данные лица;
- содержание оснований исключения зависимостей.

Доступ: руководитель кабинета, руководитель Группы, владелец
соответствующей инициативы.

### 3.5. Уровни разграничения

По портфелю · по инициативе · по подразделению · по типу данных ·
по отдельным полям · по уровню конфиденциальности.

**Правило конфликта:** применяется наиболее ограничительное
из применимых правил.

### 3.6. Обязательное журналирование

Просмотр чувствительных полей · изменение статуса достоверности ·
подтверждение и утверждение · изменение назначений ролей ·
связывание и разъединение лица с учётной записью · изменение
прав доступа · экспорт · административное исключение зависимости.

## 4. Обследование таблицы подразделений

**Разрешено вами как исследование без изменений.**

### 4.1. Программа обследования — 9 пунктов

| № | Что обследовать |
|---|---|
| 1 | Структура таблицы: перечень полей и типов |
| 2 | Владелец данных |
| 3 | Использование существующими разделами системы |
| 4 | Иерархия: механизм и глубина |
| 5 | Идентификаторы: тип, стабильность, уникальность |
| 6 | История изменений: наличие версионности |
| 7 | Полнота и качество данных |
| 8 | Ограничения доступа |
| 9 | Варианты повторного использования без повреждения |

### 4.2. Строгие ограничения

**Запрещено:** менять структуру · выполнять миграции · добавлять
или исправлять записи · создавать дублирующий справочник ·
менять контракты API · менять зависимые разделы.

**Разрешено:** чтение схемы, чтение данных, анализ связей.

### 4.3. Формат результата

Отдельная записка с обоснованием одного из вариантов:

| Вариант | Условие |
|---|---|
| Использовать существующую таблицу без изменений | Пригодна полностью |
| Профильное расширение (отдельная таблица один-к-одному) | Пригодна, но менять нельзя |
| Слой сопоставления | Непригодна по качеству |
| Иной вариант с обоснованием | По результатам |

**Обследование не выполнено** — жду подтверждения, что его можно
начинать в текущей итерации, поскольку продуктовый код заморожен.
