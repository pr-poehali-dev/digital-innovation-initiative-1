## 2. Уточнённая формулировка независимости — принята дословно

> **Правило независимого подтверждения действует без ролевых
> исключений. Аварийное принятие собственной записи по
> исключению допускается отдельно и не является независимым
> подтверждением.**

Формулировка зафиксирована как основная в терминологии проекта.
`accepted_by_exception` для собственной записи **не считается
исключением из правила независимости**, поскольку само по себе
**не является подтверждением** — это отдельная, явно иначе
поименованная операция.

## 3. Различение причин прекращения исключения

**Принято требование:** истечение календарного срока и досрочное
прекращение из-за содержательного изменения должны быть
различимы в аудите, хотя оба лишают исключение действующей силы.

### 3.1. Шесть различаемых сведений аудита

Полный набор полей, обязательный для аудита исключения:

| № | Поле | Назначение |
|---|---|---|
| 1 | `exception_expires_at` | **Плановый срок** — установлен при создании исключения |
| 2 | `exception_terminated_at` | **Фактический момент прекращения** — когда исключение реально утратило силу (может отличаться от планового при досрочном прекращении) |
| 3 | `exception_termination_reason` | **Причина прекращения** — `expired` / `invalidated_by_change` / `null` |
| 4 | `exception_terminating_change_ref` | **Изменение, прекратившее исключение** — заполняется только при `invalidated_by_change`, ссылка на конкретное изменение записи |
| 5 | `exception_terminating_change_author` | **Пользователь, выполнивший изменение** — заполняется только при `invalidated_by_change` |
| 6 | `exception_prior_basis` | **Прежнее основание исключения** — текст основания, под которым исключение было установлено, сохраняется неизменным после прекращения |

Дополнительно вычисляемое поле:

| Поле | Назначение |
|---|---|
| `exception_active` | Вычисляемое: `false`, если исключение утратило силу по любой причине |

### 3.1a. Непротиворечие `exception_expired` и причины прекращения

**Обязательное правило:** признак `exception_expired`
(из `rev2-13`) и `exception_termination_reason` **не должны
противоречить друг другу**.

| Ситуация | `exception_termination_reason` | `exception_expired` |
|---|---|---|
| Исключение действует | `null` | `false` |
| Наступил календарный срок, изменений не было | `expired` | **`true`** |
| Досрочно прекращено изменением, **срок ещё не наступил** | `invalidated_by_change` | **`false`** — не называется просроченным |
| Досрочно прекращено изменением, **срок уже наступил бы позже, но событие раньше** | `invalidated_by_change` | `false` до планового `exception_expires_at`, далее вычисление не имеет смысла — причина уже зафиксирована как `invalidated_by_change` и не переписывается |

**Ключевое правило:** если исключение прекращено изменением
до наступления планового срока, оно **недействительно, но не
называется просроченным** до фактического наступления
`exception_expires_at`. Поле `exception_termination_reason`,
однажды установленное в `invalidated_by_change`, **не
перезаписывается** на `expired` при последующем наступлении
календарного срока — причина прекращения фиксируется в момент
события и является исторической.

### 3.2. Допустимые значения `exception_termination_reason`

| Код | Причина | Что фиксируется дополнительно |
|---|---|---|
| `expired` | Истёк календарный срок (`exception_expires_at` в прошлом, UTC) | Дата истечения — совпадает с `exception_expires_at` |
| `invalidated_by_change` | Досрочно прекращено содержательным изменением записи | Дата и автор изменения, которое прекратило исключение |
| `null` | Исключение продолжает действовать | — |

**Переименовано с `superseded_by_change` на `invalidated_by_change`**
— точнее отражает смысл (запись не «замещена», а исключение
«признано недействительным» изменением). Выбор кода
зафиксирован **до создания схемы**, чтобы избежать миграции
переименования после появления данных.

**Оба случая лишают исключение силы одинаково** с точки зрения
допустимости операций (`X03` из `rev2-13`), но причина в аудите
**не смешивается**.

### 3.3. Поведение по каждой причине

| Аспект | `expired` | `invalidated_by_change` |
|---|---|---|
| Момент фиксации | В момент проверки признака `exception_expired`, дата истечения известна заранее | В момент содержательного изменения — событие, а не таймер |
| Что становится недействительным | Только исключение | Исключение **и** предыдущее содержание записи |
| Требуется ли новое решение | Да — новое исключение или независимая проверка | Да — новое исключение или независимая проверка **для изменённого содержания** |
| История прежнего исключения | Сохраняется целиком | Сохраняется целиком |

### 3.4. Отображение в аудите

```
Запись: role_assignment #4821
├─ 10.08.2026 09:00  accepted_by_exception
│                     основание: «отсутствие второго редактора»
│                     срок: 17.08.2026 23:59 UTC
│                     автор: управляющий кабинетом
│
└─ 15.08.2026 14:22  exception_active → false
                      причина: invalidated_by_change
                      прекращено изменением: смена субъекта роли
                      автор изменения: редактор Х
```

```
Запись: decision_instance #190
├─ 10.08.2026 09:00  accepted_by_exception
│                     срок: 12.08.2026 23:59 UTC
│
└─ 13.08.2026 00:00  exception_active → false
                      причина: expired
                      (календарный срок наступил, изменений
                       содержания не было)
```

**Обе ситуации визуально и структурно различимы.**

## 4. Условия `approved_via` — полный набор

### 4.1. Ограничение на использование `accepted_by_exception`

**Принято дословно:** значение `approved_via = accepted_by_exception`
допустимо **только при наличии отдельного решения**, разрешающего
утверждение без независимого подтверждения. Сам факт нахождения
записи в статусе `accepted_by_exception` **автоматически
`approved` не порождает**.

### 4.2. Обязательные поля решения об утверждении через исключение

| Поле | Назначение |
|---|---|
| `approval_decision_ref` | Ссылка или идентификатор **отдельного** решения, разрешающего утверждение без независимого подтверждения |
| `approval_decision_author` | Автор решения об утверждении |
| `approval_decision_date` | Дата решения |
| `approval_decision_basis` | Основание |
| `approval_based_on_exception_ref` | Ссылка на **действовавшее** исключение (`accepted_by_exception`), на котором основано утверждение |
| `approval_exception_expires_at` | Срок этого исключения **на момент утверждения** — сохраняется как снимок, не пересчитывается впоследствии |
| `retrospective_review_result` | Результат последующей ретроспективной проверки — заполняется отдельно, когда проверка состоится |

**Все семь полей обязательны** при `approved_via =
accepted_by_exception`. При `approved_via = confirmed`
поля, специфичные для исключения, не заполняются.

### 4.3. Три различаемых состояния исключения при `approved`

**Принято:** должно сохраняться различие между состоянием
исключения **на момент утверждения** и его **текущим** и
**последующим** состоянием.

| № | Состояние | Поле | Изменяемость после `approved` |
|---|---|---|---|
| 1 | Состояние исключения **на момент утверждения** | `approval_exception_expires_at` (снимок из 4.2) | **Неизменно** — фиксируется один раз |
| 2 | **Текущее** состояние связанного исключения | Читается из самой записи исключения (`exception_active`, `exception_termination_reason` — разд. 3.1) | Изменяется независимо от `approved`, по факту истечения или прекращения |
| 3 | **Последующий результат** ретроспективной проверки | `retrospective_review_result` (поле из 4.2) | Заполняется отдельно, когда проверка состоится |

Эти три сведения **не смешиваются в одно поле** — каждое
отвечает на свой вопрос: что было известно при утверждении,
что известно сейчас, что решено при последующей проверке.

### 4.4. Прозрачность без автоматического отзыва

**Принято дословно:** до решения открытого вопроса о влиянии
последующей просрочки исключения на уже утверждённую запись,
система **не отзывает `approved` автоматически**, но
**сохраняет видимость** основания и его последующего состояния.

| Ситуация | Отображение |
|---|---|
| `approved` установлен, исключение позже истекло (`exception_termination_reason = expired`) | `approved` **сохраняется** формально; отображается предупреждение: «Утверждено на основании исключения, впоследствии истёкшего {дата}» |
| `approved` установлен, исключение позже прекращено изменением (`exception_termination_reason = invalidated_by_change`) | `approved` **сохраняется** формально; отображается предупреждение: «Утверждено на основании исключения, впоследствии признанного недействительным {дата}, изменение: {ссылка}» |
| `approved` установлен, исключение на момент утверждения **уже не действовало** | Невозможно — `approval_based_on_exception_ref` требует действовавшего исключения на дату `approval_decision_date` |

**Автоматический отзыв `approved`** — не выполняется ни в
одном случае, пока не принято отдельное решение.

**Видимость сохраняется всегда:** текущее состояние связанного
исключения (п. 2 из разд. 4.3) читается «вживую» при каждом
просмотре карточки утверждённой записи — предупреждение не
статично, оно отражает состояние исключения на момент
просмотра, а не только на момент утверждения.

### 4.5. Открытый вопрос остаётся открытым

**Зафиксировано как открытое, по вашему указанию:** конкретная
реакция уже утверждённой записи на последующую просрочку
лежавшего в её основе исключения **не решается сейчас** —
отдельный вопрос реализации следующего этапа.

**Решается сейчас:** сам факт прохождения через исключение
**не скрывается** — виден в `approved_via` и в семи
сопроводительных полях бессрочно, независимо от дальнейшей
судьбы исключения; текущее состояние исключения видно отдельно
от снимка на момент утверждения.
