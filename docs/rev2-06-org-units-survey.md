## 2. Схема, ключи, ограничения, связи

**Таблица:** `org_units`

| Поле | Тип | Ограничения |
|---|---|---|
| `id` | integer | Первичный ключ, автоинкремент |
| `project_id` | integer | NOT NULL |
| `code` | text | NOT NULL, по умолчанию пусто |
| `name` | text | NOT NULL |
| `type` | text | NOT NULL, по умолчанию `division` |
| `parent_id` | integer | NULL, **внешний ключ на себя** |
| `path` | text | NOT NULL, материализованный путь |
| `level` | integer | NOT NULL, глубина |
| `sort_order` | integer | NOT NULL |
| `source_document_id` | integer | NULL |
| `source_ref` | text | NOT NULL, по умолчанию пусто |
| `created_at` | timestamptz | NOT NULL |
| `updated_at` | timestamptz | NOT NULL |
| `is_archived` | boolean | NOT NULL, по умолчанию `false` |

**Обнаруженные особенности:**

1. **Нет ограничения уникальности** на `(project_id, code)` —
   уникальность кода обеспечивается только логикой приложения.
2. **Нет ограничения на `type`** — свободный текст, не справочник.
3. Иерархия реализована **двумя способами одновременно**:
   `parent_id` и материализованный `path` с `level`. Требуется
   синхронизация при изменениях.
4. `source_document_id` объявлен, но **не используется** —
   заполнен в 0 записях.
5. `source_ref` — текстовое поле, не ссылка на сущность.

**Связанные таблицы:** `function_org_units` (связь с функциями),
`macro_process_units` (связь с группами функций).

## 3. Владелец и фактический источник данных

| Параметр | Значение |
|---|---|
| Технический владелец | Функция `dept-functions` — операции создания и изменения |
| Второй потребитель | Функция `process-map` — только чтение |
| Фактический источник | Загрузка из документов организации + ручное редактирование через интерфейс |
| Признак источника | Поле `source_ref`, заполнено у **10 из 20** записей |

**Вывод:** единого внешнего источника-владельца нет. Данные
формируются внутри системы из двух путей: разбор документов
и ручной ввод. Внешняя кадровая или организационная система
не подключена.

## 8. Четыре варианта повторного использования

### Вариант А. Использовать без изменений

**Суть:** кабинет ссылается на `org_units.id`, дополнительные
атрибуты не хранятся.

| Плюсы | Минусы |
|---|---|
| Нулевой риск для существующих модулей | Нет руководителя подразделения |
| Не требует миграций | Нет цели и зоны ответственности |
| Единый источник структуры | Нет статуса достоверности |
| Готово немедленно | Нет истории изменений |

**Применимость:** достаточно для MVP, если подразделение нужно
только как ссылка при указании стейкхолдера или заказчика
инициативы.

---

### Вариант Б. Профильное расширение

**Суть:** отдельная таблица `org_unit_profile` со связью
один-к-одному, хранит только атрибуты кабинета.

| Плюсы | Минусы |
|---|---|
| Существующая таблица не изменяется | +1 таблица к реестру |
| Существующие модули не затрагиваются | Требуется соединение при выборках |
| Можно добавить руководителя, цель, статус | Риск рассинхронизации при удалении |
| Своя история изменений | — |

**Применимость:** если в MVP нужны руководитель подразделения
и статус достоверности.

**Внимание:** это **+1 таблица** к согласованным 16.

---

### Вариант В. Слой сопоставления

**Суть:** таблица соответствия внутренних кодов кабинета
и идентификаторов `org_units`.

| Плюсы | Минусы |
|---|---|
| Независимость от изменений в существующей таблице | Дублирование понятий |
| Возможен переход на внешний источник | Сложность поддержки |
| — | Риск расхождения справочников |

**Применимость:** только если планируется подключение внешней
организационной системы. Признаков такой системы **не обнаружено**.

---

### Вариант Г. Признать непригодной

**Доказательства непригодности отсутствуют.**

Таблица структурно целостна: 0 нарушенных ссылок, 0 дублей,
рабочая иерархия, механизм архивирования. Непригодной
признать нельзя.

## 9. Рекомендация

**Рекомендую вариант А для MVP** с последующим переходом
к варианту Б при необходимости.

**Обоснование:**

1. В двух сценариях MVP подразделение используется как **ссылка**:
   заказчик инициативы и стейкхолдер-подразделение. Дополнительные
   атрибуты для построения матриц **не требуются**.
2. Таблица структурно пригодна, риск нулевой.
3. Вариант Б добавляет 17-ю таблицу ради атрибутов, не участвующих
   в двух согласованных сценариях.
4. Переход А → Б возможен позже без переделки: профильная таблица
   добавляется, ссылки не меняются.

**Условие пересмотра:** если в MVP потребуется указывать
руководителя подразделения как отдельную сущность либо вести
статус достоверности подразделения — переходим к варианту Б
с явным увеличением реестра до 17 таблиц.

**Изменения не вносились. Решение за вами.**
