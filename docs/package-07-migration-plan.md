## 1. Порядок миграций

Разбит на 5 этапов. Каждый этап работоспособен самостоятельно.

### Этап 1. Справочники и общая инфраструктура

`V0278__create_reference_dictionaries`

Таблицы:
- `ref_lifecycle_status` — статусы жизненного цикла
- `ref_origin_type` — типы происхождения
- `ref_confidence_level` — уровни уверенности
- `ref_confidentiality` — уровни конфиденциальности
- `ref_initiative_status`, `ref_initiative_stage`
- `ref_realization_form`, `ref_solution_type`
- `ref_role_type`, `ref_influence_level`
- `ref_attitude`, `ref_engagement_strategy`
- `ref_participation_type`, `ref_escalation_level`
- `ref_decision_status`, `ref_execution_status`
- `ref_effect_type`, `ref_source_type`

Структура справочника: `id`, `code` (уникальный), `name`,
`description`, `sort_order`, `is_active`, `is_system`.

Признак `is_system` защищает базовые значения от удаления
пользователем, при этом справочник остаётся расширяемым.

`V0279__create_source_ref`
- `source_ref` — универсальные ссылки на источники
  Поля: `id`, `entity_type`, `entity_id`, `field_name`,
  `source_type_code`, `title`, `document_link`, `quote`,
  `page_section`, `document_date`, `edition`, `confidence_code`,
  `verified_by`, `verified_at`, служебные поля.
  Индексы: `(entity_type, entity_id)`, `(entity_type, entity_id, field_name)`.

`V0280__create_audit_log`
- `mgmt_audit_log` — журнал действий
  Поля: `id`, `user_id`, `action`, `entity_type`, `entity_id`,
  `field_name`, `old_value`, `new_value`, `ip_address`,
  `created_at`.
  Индексы: `(entity_type, entity_id)`, `(user_id, created_at)`.

### Этап 2. Справочник лиц и организационная структура

`V0281__create_person_position`
- `person` — единый справочник лиц
  Ключевые поля: `id`, `person_code` (уникальный, для условных
  обозначений), `display_name`, `last_name`, `first_name`,
  `middle_name`, `is_external`, `organization`, `is_active`,
  `substitute_person_id` (самоссылка), `confidentiality_code`,
  `lifecycle_status_code`, `is_test_data`, служебные поля.
  Индексы: `person_code` (unique), `lower(display_name)`, `is_active`.
  Ограничение: `person_code` не может быть пустым.

- `position` — должности
  Поля: `id`, `name`, `org_unit_id`, `parent_position_id`,
  `category`, `responsibility_area`, `normative_basis`,
  `is_vacant`, `is_active`, служебные.

- `person_position` — связь лица и должности с историей
  Поля: `id`, `person_id`, `position_id`, `date_from`, `date_to`,
  `is_current`.

**Решение по подразделениям — требует согласования.**
Вариант А: расширить существующую `org_units` полями
`short_name`, `purpose`, `responsibility_area`, `head_person_id`,
`formation_status`, `normative_basis`.
Вариант Б: создать `mgmt_org_unit` и связать с `org_units`.
**Рекомендую вариант А** — существующая таблица уже содержит
иерархию, коды и типы; дублирование создаст рассинхронизацию.

### Этап 3. Инициативы, решения-продукты, эффекты

`V0282__create_initiative`
- `initiative` — центральная таблица
  Внешние ключи: `org_unit_id`, `initiator_person_id`.
  Ссылки на справочники по `code`, не по `id` — для читаемости
  запросов и устойчивости к пересозданию справочников.
  Индексы: `(status_code, stage_code)`, `org_unit_id`,
  `is_test_data`, `lifecycle_status_code`.

- `project_form` — форма реализации «проект»
  Ограничение: `UNIQUE(initiative_id)` — одна инициатива,
  не более одного проекта.

`V0283__create_solution_effect`
- `mgmt_solution` — создаваемые решения
- `initiative_solution` — связь N..N инициатив и решений
- `effect` — эффекты
  Поля значений: `baseline_value`, `target_value`, `actual_value`,
  `measurement_method`, `owner_person_id`, `confirmation_doc_id`.

`V0284__create_milestone_issue_risk`
- `milestone` — контрольные точки
- `issue` — проблемы
- `risk` — риски
- `escalation` — эскалации
  Все с полем `initiative_id` и индексом по нему.

### Этап 4. Роли, стейкхолдеры, решения

`V0285__create_role_catalog`
- `role_template` — каталог типовых ролей
  Поле `is_exclusive` — признак единоличной роли.
- `role_assignment` — назначения ролей
  Ограничение: при `is_exclusive = true` в шаблоне —
  частичный уникальный индекс на `(initiative_id, role_id)`
  где `status = 'active'`.
  Индексы: `initiative_id`, `person_id`, `(initiative_id, role_id)`.

`V0286__create_stakeholder`
- `stakeholder` — стейкхолдеры инициативы
  Ограничение: `UNIQUE(initiative_id, person_id)` и
  `UNIQUE(initiative_id, org_unit_id)` — частичные, поскольку
  стейкхолдером может быть либо лицо, либо подразделение.
  Проверка: `CHECK (person_id IS NOT NULL OR org_unit_id IS NOT NULL)`.
  Числовые поля: `influence_level` и `interest_level` —
  `CHECK (BETWEEN 1 AND 5)`.
- `engagement_strategy` — стратегии
- `engagement_action` — действия по взаимодействию
  Индекс: `(planned_date, status)` для выявления просрочек.

`V0287__create_decision_model`
- `decision_type` — каталог типов решений
- `decision_instance` — экземпляры решений
  Проверка: `CHECK (decided_at IS NULL OR decided_at >= raised_at)` —
  реализация правила E06 на уровне БД.
- `decision_participation` — участие ролей в решениях
  Индексы: `(decision_type_id)`, `(decision_instance_id)`,
  `(role_id)`, `(participation_type_code)`.
- `decision_dependency` — **зависимости между решениями**
  Добавлено по итогам тестового сценария: решение №9 невозможно
  без №6. Поля: `decision_id`, `depends_on_decision_id`,
  `dependency_type`.
  Проверка: запрет самоссылки и циклов.

## 2. Ключи, связи, индексы

**Первичные ключи:** `SERIAL PRIMARY KEY` везде — единообразно
с существующей схемой проекта.

**Внешние ключи:** с явным `ON DELETE RESTRICT` по умолчанию.
Каскадное удаление **не применяется** нигде — вместо удаления
используется архивирование.

**Ссылки на справочники:** по полю `code` (VARCHAR), а не по `id`.
Обоснование: читаемость запросов, устойчивость при пересоздании
справочников, совместимость с Simple Query Protocol.

**Обязательные индексы:**
- по всем внешним ключам;
- по полям фильтрации: `lifecycle_status_code`, `is_test_data`,
  `is_active`;
- по датам для выявления просрочек: `planned_date`, `due_date`;
- частичные уникальные индексы для единоличных ролей.

## 3. Ограничения целостности

Реализуемые на уровне БД:

| Правило | Реализация |
|---|---|
| E06 — дата принятия ≥ даты возникновения | `CHECK` в `decision_instance` |
| E10 — проект только при наличии инициативы | `NOT NULL` + `FK` |
| E11 — влияние и заинтересованность 1–5 | `CHECK BETWEEN 1 AND 5` |
| Одна инициатива — один проект | `UNIQUE(initiative_id)` |
| Единоличная роль — одно назначение | Частичный уникальный индекс |
| Стейкхолдер — лицо или подразделение | `CHECK` на непустоту одного из полей |

Реализуемые на уровне приложения (требуют вычислений):
E01, E02, E03, E04, E05, E07, E08, E09, E12 и все предупреждения.

## 4. Аудит изменений

**Решение — на согласование** (открытый вопрос №5 части 3).

Вариант А: единая таблица `mgmt_audit_log` для всех сущностей.
Плюсы: простота, единый интерфейс истории.
Минусы: рост объёма, менее удобные выборки.

Вариант Б: поля `created_by/at`, `updated_by/at` в каждой таблице
плюс отдельный журнал только для критичных действий.
Плюсы: меньше объём.
Минусы: неполная история изменений полей.

**Рекомендую вариант А** для управленческого контура —
здесь важна прослеживаемость решений и полномочий.

## 5. Мягкое удаление

Физическое удаление запрещено для всех сущностей модели.

Механизм: поля `archived_at`, `archived_by`, `archive_reason`.
Все выборки по умолчанию фильтруют `archived_at IS NULL`.
Просмотр архива — отдельное право доступа.

## 6. Порядок отката

Миграции проекта forward-only, автоматический откат недоступен.

**Стратегия безопасности:**

1. Все миграции этапов 1–4 — **только создание новых таблиц**.
   Существующие таблицы и данные не затрагиваются. Риск минимален.
2. Миграция V0288 изменяет существующую `glossary_terms` —
   **добавление** столбца, без удаления данных. Обратимо
   логически: столбец можно перестать использовать.
3. Откат создания таблиц выполняется отдельной миграцией
   `DROP TABLE`, подготовленной заранее, — но требует отдельного
   согласования, поскольку удаляет данные.

**Резервное копирование:** перед выполнением этапа, изменяющего
существующие таблицы (V0288), необходима выгрузка затрагиваемых
таблиц. Требуется подтверждение, что механизм резервного
копирования доступен.

## 7. Перенос тестовых данных

Тестовая инициатива ТЕСТ-01 создаётся отдельной миграцией
`V0290__seed_test_initiative` **после** утверждения модели.

Все записи с `is_test_data = true`.
Удаление тестовых данных — отдельной миграцией по одному признаку,
без риска затронуть реальные данные.

**Порядок наполнения:** справочники → лица → роли → инициатива →
назначения ролей → стейкхолдеры → типы решений → экземпляры
решений → участие ролей в решениях → зависимости решений.
