## 2. Правила валидации

Три категории. Первые две — **детерминированные правила**, не ИИ.

### 2.1. Блокирующие ошибки

Не позволяют перевести объект в статус «подтверждено» или «утверждено».

| Код | Правило | Объект |
|---|---|---|
| `E01` | У решения нет участника с видом «принимает окончательное решение» | Решение |
| `E02` | Несколько участников принимают окончательное решение, порядок коллегиального решения не указан | Решение |
| `E03` | У инициативы нет владельца | Инициатива |
| `E04` | Роль назначена, но не указано лицо или подразделение | Назначение роли |
| `E05` | Подтверждённое полномочие не имеет основания | Участие в решении |
| `E06` | Дата принятия решения раньше даты возникновения вопроса | Решение |
| `E07` | Инициатива закрыта без указания результата или основания | Инициатива |
| `E08` | Статус «подтверждено»/«утверждено» без указания источника | Любой объект |
| `E09` | Экземпляр решения не связан с инициативой | Решение |
| `E10` | Проект создан без инициативы | Проект |
| `E11` | У стейкхолдера не задан уровень влияния или заинтересованности | Стейкхолдер |
| `E12` | Эффект подтверждён без документа-основания | Эффект |

### 2.2. Предупреждения

Не блокируют работу, отображаются на главном экране и в диагностике.

| Код | Правило |
|---|---|
| `W01` | Отсутствует владелец эффекта |
| `W02` | Не указано замещающее лицо для единоличной роли |
| `W03` | Стейкхолдер с влиянием 4–5 не имеет стратегии взаимодействия |
| `W04` | Влиятельный оппонент не имеет ближайшего действия |
| `W05` | Превышено рекомендуемое количество согласований (порог настраиваемый, по умолчанию 5) |
| `W06` | Решение просрочено относительно требуемой даты |
| `W07` | Один участник принимает решения более чем в N инициативах (порог настраиваемый) |
| `W08` | Не определён маршрут эскалации для решения |
| `W09` | Ответственность без полномочий: роль отвечает за результат, но не имеет права принять ни одно связанное решение |
| `W10` | Полномочие без ответственности: роль принимает решения, но не отвечает ни за один результат |
| `W11` | Отсутствует владелец создаваемого решения |
| `W12` | Инициатива не имеет ни одной контрольной точки |
| `W13` | Контрольная точка просрочена |
| `W14` | Действие по взаимодействию просрочено |
| `W15` | Данные не актуализировались более установленного срока |
| `W16` | Инициатива без подтверждённого эффекта на этапе закрытия |

### 2.3. AI-рекомендации

| Код | Рекомендация |
|---|---|
| `A01` | Возможный отсутствующий стейкхолдер |
| `A02` | Вероятный конфликт интересов между участниками |
| `A03` | Предложение стратегии взаимодействия |
| `A04` | Вопросы к предстоящей встрече |
| `A05` | Возможное упрощение маршрута согласования |
| `A06` | Похожая инициатива уже существует в портфеле |
| `A07` | Предложение формулировки эффекта и способа измерения |
| `A08` | Риск, характерный для данного типа инициативы |

**Обязательные свойства AI-рекомендаций:**
не блокируют работу; сохраняются со статусом `ai_draft`; содержат
объяснение основания; **не изменяют карточки автоматически**;
требуют явного подтверждения или отклонения человеком; при отклонении
сохраняется причина.

## 3. Модель доступа

### 3.1. Роли доступа

| Роль | Назначение |
|---|---|
| `administrator` | Администратор системы |
| `cabinet_head` | Руководитель кабинета |
| `group_head` | Руководитель Группы |
| `initiative_owner` | Владелец инициативы |
| `initiative_manager` | Руководитель инициативы |
| `participant` | Участник |
| `observer` | Наблюдатель |

### 3.2. Матрица прав

Обозначения: **+** полный доступ · **±** в рамках своих инициатив ·
**−** нет доступа

| Действие | Админ | Рук. кабинета | Рук. Группы | Владелец иниц. | Рук. иниц. | Участник | Наблюдатель |
|---|---|---|---|---|---|---|---|
| Просмотр портфеля | + | + | + | ± | ± | ± | ± |
| Создание инициативы | + | + | + | ± | − | − | − |
| Редактирование инициативы | + | + | + | ± | ± | − | − |
| Подтверждение данных | + | + | ± | ± | − | − | − |
| Утверждение | − | + | − | − | − | − | − |
| Архивирование | + | + | ± | ± | − | − | − |
| Экспорт | + | + | + | ± | ± | − | − |
| Просмотр истории | + | + | + | ± | ± | − | − |
| Просмотр чувствительных полей | − | + | ± | ± | − | − | − |
| Управление доступом | + | + | − | − | − | − | − |
| Управление справочниками | + | + | − | − | − | − | − |
| Назначение ролей | + | + | + | ± | − | − | − |
| Ведение стейкхолдеров | + | + | + | ± | ± | − | − |
| Ведение решений | + | + | + | ± | ± | − | − |
| Обновление своих действий | + | + | + | + | + | + | − |

**Пояснение по администратору.** Администратор осуществляет техническое
администрирование и не должен видеть чувствительные управленческие
оценки. Просмотр чувствительных полей и утверждение ему недоступны.
Это осознанное разделение технической и содержательной ролей —
**выносится на согласование**.

### 3.3. Чувствительные поля с повышенным ограничением

Доступны только: руководитель кабинета, руководитель Группы,
владелец соответствующей инициативы.

- текущее и целевое отношение стейкхолдера
- опасения стейкхолдера
- риск сопротивления
- неформальные интересы
- стратегия продвижения и ключевые сообщения
- персональные контактные данные
- содержание эскалаций
- AI-оценки в отношении конкретных лиц
- позиция стейкхолдера в истории взаимодействия

### 3.4. Уровни разграничения

Доступ определяется пересечением шести измерений:

1. **По портфелю** — доступ к определённому набору инициатив
2. **По инициативе** — участие в конкретной инициативе
3. **По подразделению** — данные своего подразделения
4. **По типу данных** — инициативы, стейкхолдеры, решения, эффекты
5. **По отдельным полям** — чувствительные поля внутри доступной карточки
6. **По уровню конфиденциальности** — метка на конкретной записи

**Правило разрешения конфликта:** применяется наиболее ограничительное
из применимых правил.

### 3.5. Требования к журналированию

Фиксируются: просмотр чувствительных полей; изменение статуса
достоверности; подтверждение и утверждение; изменение назначений
ролей; изменение прав доступа; экспорт данных; обращение к архивному
слою в режиме аудита; подтверждение и отклонение AI-рекомендаций.

## 4. Открытые вопросы по доступу

1. Должен ли администратор иметь доступ к чувствительным полям?
   Предлагаю нет — требуется ваше решение.
2. Кто утверждает данные в отсутствие руководителя кабинета?
3. Нужен ли доступ уровня «Секретарь Группы» с правом ведения
   повестки и протокола, но без права подтверждения?
4. Требуется ли ограничение доступа между инициативами разных
   подразделений Блока внутреннего контроля?
5. Требуется ли режим полной анонимизации для демонстрации
   на совещаниях?
